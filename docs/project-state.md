# Project State & Roadmap

## 1. Current Architecture Status

Candied has transitioned to a **modular, offline-first progressive reverse engineering and asset extraction architecture**. The brittle runtime companion bridge (which required launching the game, polling IPC files, and injecting uncompiled C# files into BepInEx) has been completely removed and replaced by **direct offline asset extraction from Unity archives (.assets and AssetBundles) on disk**.

  - `dotnet test --configuration Release`: 255 passing tests across Architecture (6) and Unit/Integration/E2E (249) slices, plus 5 explicit interactive/live game tests.
  - `dotnet list package --vulnerable --include-transitive`: 0 vulnerable packages across all 10 projects (`Microsoft.Data.Sqlite` upgraded to `9.0.23`, resolving transitive `GHSA-2m69-gcr7-jv3q`); GitHub Actions CI workflow scoped with least-privilege `permissions: contents: read`.
  - **29 MCP tools advertised** (added `search-code`, `add-reference`, `inspect-runtime-assets`; upgraded `query`, `type`, `discover-assets`, `inspect-scene-objects`, `build`, `game-launch`, `scene-info`). See [`docs/tool-ergonomics-roadmap.md`](./tool-ergonomics-roadmap.md) and [`docs/mcp-update-guide.md`](./mcp-update-guide.md). ## 3. Implemented Capabilities (Progressive Decompilation Flow)

1. **Phase 0 (Online Research):** Agent conducts external web research and saves structured findings into Zone 3 (`RESEARCH.md`) using `notes`.
2. **Phase 1 (Environment Audit):** `inspect` non-destructively probes target game directory, reports machine architecture, BepInEx installation status and version, target .NET framework, and categorizes assemblies into:
   - `AssemblyTier.CoreGame` (`[GameName].*.dll`, `Assembly-CSharp.dll`)
   - `AssemblyTier.GameModular`
   - `AssemblyTier.AuxiliaryOrThirdParty` (Unity, BCL, DOTween, etc.)
   along with cached/decompiled status (`isDecompiled`).
3. **Phase 1.5 (Automated & Reversible Environment Setup):** If BepInEx is missing or misconfigured, the agent calls `setup`. Candied downloads the architecture-matched release (x64/x86) to `.candied/cache/bepinex/`, extracts it to the game directory, preconfigures `BepInEx.cfg` logging, and writes `.candied_manifest.json`. If uninstallation is needed, `rollback` cleanly removes all tracked files without touching vanilla assets.
4. **Phase 2 (Selective Decompilation & Knowledge Hub Generation):** `decompile` allows the AI agent to decompile a single target assembly at a time into an isolated directory (`decompiled/<AssemblyName>/`), updates SQLite `index.db` without wiping other assemblies, and automatically updates Knowledge Hub artifacts (`GAME_OVERVIEW.md`, `NAMESPACES.md`, `SYMBOLS_INDEX.json`) with cumulative counts.
5. **Phase 3 (Symbol Discovery):** `query` and `type` allow instant querying of classes, methods, and full source code against the game's SQLite index.
6. **Phase 3.5 (Direct Offline Unity Asset Discovery & Extraction):**
   - Core Domain contracts: `IAssetExtractor`, `DiscoveredAssetInfo`, `ExtractedAssetInfo`, `DiscoverAssetsUseCase`, `ExtractAssetsUseCase`.
   - Infrastructure adapter: `AssetsToolsAssetExtractorAdapter` in `Candied.Decompiler`. Automatically locates and parses Unity `.assets` files (such as `resources.assets`, `sharedassets*.assets`) and Addressable `.bundle` files in `StreamingAssets`.
   - Zero game launch overhead: Operates entirely offline on disk files, deserializing textures and sprite slices directly to PNGs in Zone 3 (`.candied/games/<Game>/assets/`).
   - Agent MCP & CLI tools: `discover-assets` (`discover-assets`) and `extract-assets` (`extract-assets`).
7. **Phase 4 (Modding & Build):** `scaffold` and `build` generate and verify the mod project with compiler diagnostics. The loose asset pipeline is strictly opt-in (`includeAssetPipeline: true` or `--with-assets`); when enabled, MSBuild deploys loose assets directly into `BepInEx/plugins/<ModName>/Assets/` and scaffolds `AssetLoader.cs` for runtime disk loading, keeping mod assets visible and editable instead of compiling them inside the DLL. MSBuild path normalization guarantees reliable builds with relative paths.
8. **Phase 5 (Runtime Logs):** `logs` tails and parses `BepInEx/LogOutput.log`.
9. **Phase 6 (Embedded Live Inspection & Game Host - Candied.Studio):**
   - WPF .NET 9 desktop host providing embedded native execution of generic Unity Mono games.
   - Airspace-isolated two-column layout avoiding WPF HwndHost rendering overlap.
   - Deterministic Windows Job Object process tree termination with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`.
   - Direct launch with `-parentHWND` and fallback window locator heuristics via `Toolhelp32` process tree traversal (`UnityWndClass` matching).
   - Fixed resolution startup (`-screen-width 1024 -screen-height 720 -screen-fullscreen 0`) paired with host-side aspect-ratio letterbox / pillarbox calculator (`ViewportCalculator`).
   - Bidirectional coordinate transformations (`GameToPanelCoordinates`, `PanelToGameCoordinates`).
   - Real-time BepInEx log monitoring.
   - Experimentally verified on clean copy of *Unity Mono Target Game* (Unity Mono, x64).
10. **Phase 7 (In-Game Vision Bridge & Semantic Perception - Candied.VisionBridge):**
   - Multi-target BepInEx 5 plugin (`Candied.VisionBridge`, `net35;net472`) running in-game local HTTP server on `127.0.0.1:{CANDIED_PORT}` with strict token authentication (`X-Candied-Token`), returning HTTP 401 with zero-body payload on missing/invalid token without leakage.
   - Strict `Host` header validation (`127.0.0.1`) rejecting unexpected origins with HTTP 403 (zero CORS).
   - Main thread task queue (`MainThreadDispatcher`) drained on `Update()`.
   - Pure reflection capability discovery (`CapabilitiesDetector`) for optional Unity modules (`UnityEngine.UI`, `UIElements`, `InputSystem`, `ScreenCapture`), dynamically reporting active `ScreenshotMethod` (`camera_fallback` vs `screen_capture`) and `ScreenshotLimitations`.
   - Generic uGUI element discovery (`UguiProvider`) scanning `UnityEngine.UI.Selectable` items without game-specific types.
   - Screenshot capture (`ScreenshotCapturer`) with dual-engine pipeline: modern `ScreenCapture.CaptureScreenshotAsTexture` with automatic fallback to depth-sorted off-screen camera rendering (`CaptureViaCameras` using `RenderTexture` and `ReadPixels`), with `RenderTexture.active = null` clearing. Uniformity detection header (`X-Candied-Uniform-Image`).
   - Sizing investigation: calling `Screen.SetResolution` inside child windows breaks DirectX swapchain renegotiation; fixed launch resolution + native Win32 window resizing via `SetWindowPos` letterbox preserves rendering stability.
   - Empirical proof of `Windows.Graphics.Capture`: rejected on `WS_CHILD` handles (`E_INVALIDARG 0x80070057`), supported on top-level host HWND.
   - Host `SendInput` analysis: identified OS foreground locks, cross-process `SetFocus` limitations, and Unity New Input System raw input dropping when running in background. Documented in-process input injection requirements for Phase 8.
   - Complete purge of game-specific knowledge: 0 occurrences of custom method/type names in core or bridge.
   - Experimentally verified live on clean copy of *Unity Mono Target Game* (Unity Mono, x64, Unity 2023.1.13f1).

      * *Issue Diagnosed:* When Studio was spawned via `cmd.exe /c start` with `CreateNoWindow = true`, the child process inherited `STARTUPINFO.wShowWindow = SW_HIDE`. Win32 `ShowWindow` ignores `SW_SHOWNORMAL` on the initial call when `STARTF_USESHOWWINDOW` is set in `STARTUPINFO`, leaving the WPF window hidden.
      * *Fix Applied:* Replaced `cmd.exe` launch with direct shell execution (`UseShellExecute = true`, `WindowStyle = Normal`). Added `EnsureVisibleAndActive()` in `MainWindow`: normalizes window if minimized, clamps dimensions and coordinates to monitor work area, overrides `STARTUPINFO` with Win32 `ShowWindow(SW_SHOWNORMAL)` and `ShowWindow(SW_RESTORE)`, sets `ShowInTaskbar = true`, brings to foreground via `SetForegroundWindow`, and writes all startup events and unhandled exceptions to `%APPDATA%/Candied/logs/studio.log`.

    - **Idempotence:** Subsequent calls to `game-launch` detect the running session and return current status without spawning a duplicate instance.
    - **Deterministic Cleanup:** `game-close` shuts down the game and its entire child process tree via Windows Job Object, and removes the session file.
    - **Fixed 1024x720 Launch Resolution & Resolution Disambiguation:**
      * *Issue Diagnosed:* Previously, `game-launch` reported resolution `689x919` because `UnityGameHostController` mistakenly passed the WPF host container panel pixel dimensions (`containerPixelWidth`, `containerPixelHeight`) into `-screen-width` and `-screen-height` launch arguments for Unity.
      * *Fix Applied:* `UnityGameHostController` now always passes fixed launch arguments `-screen-width 1024 -screen-height 720 -screen-fullscreen 0 -popupwindow` to Unity. The host panel size is used exclusively for letterbox/pillarbox positioning via `ViewportCalculator`.
      * *Schema Disambiguation:* The MCP tool and HTTP status endpoint now explicitly distinguish:
        - `gameResolution` / `resolution`: `{ "width": 1024, "height": 720 }` (Unity internal `Screen.width` and `Screen.height`).
        - `panelResolution`: `{ "width": 1049, "height": 919 }` (physical dimensions of the host container panel).
        - `screenshotDimensions`: `{ "width": 1024, "height": 720 }`.
      * *Click Mapping Invariant:* Coordinates passed to `click(x, y)` originate from the 1024x720 screenshot. In-process `InputClicker` maps $Y$ directly to Unity Screen space via $UnityY = 720 - 1 - y$. Because Unity's internal backbuffer and `Screen` dimensions are 1024x720, screenshot coordinates map 1:1 to Unity screen space with zero distortion and zero letterbox offset required.
    - **DPI Scaling & Studio Window Rect Diagnostics:**
      * *Explanation:* On high-DPI displays (e.g. 150% scaling, $DpiScale = 1.50$), WPF window properties (`Width = 1000`, `Height = 650`) are defined in Device Independent Pixels (DIPs, 1/96 inch), whereas Win32 API `GetWindowRect` reports physical screen pixels ($1000 \times 1.5 = 1500$, $650 \times 1.5 = 975$).
      * *Fix Applied:* `MainWindow.EnsureVisibleAndActive()` uses `SWP_NOMOVE | SWP_NOSIZE | SWP_SHOWWINDOW | SWP_FRAMECHANGED` to avoid feeding DIP coordinates to pixel-based Win32 APIs, and `StudioLogger` logs both: `PhysicalRect: [{Left},{Top},{Right},{Bottom}] ({physicalW}x{physicalH} px), Dips: {Width}x{Height}, DpiScale: {dpi.PixelsPerDip:F2}`.
