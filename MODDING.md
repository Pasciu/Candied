# Autonomous Modding & Live Perception Guide for AI Agents (`MODDING.md`)

This guide is the operational playbook for AI agents and modders using **Candied** to inspect, reverse-engineer, mod, and visually test PC games and emulated games.

**Read this guide before invoking Candied MCP tools.**

### Multiplayer & Anti-Cheat Safety Check (Mandatory)

Candied is designed strictly for **single-player / offline modding and research** and has never been tested on multiplayer or anti-cheat-protected titles (Easy Anti-Cheat, BattlEye, VAC, Vanguard, etc.).
Before running `setup`, deploying a mod, or calling `game-launch` on any online/multiplayer game or a folder containing anti-cheat binaries:
1. **Pause and inform the user** that modding anti-cheat/online games carries a risk of account bans.
2. **Wait for explicit user confirmation** before modifying the target directory.

---

## 1. Mental Model: Three-Zone Layout & 2-Tier Vision

Candied keeps every workspace clean across three strict zones:
* **Zone 1 (`targetPath`):** The target game installation or ROM/ISO file. Kept untouched except when `setup` provisions a manifest-tracked mod loader (`.candied_manifest.json`, reversible via `rollback`) and compiled mod outputs.
* **Zone 2 (`mods/<ModName>/`):** Clean mod project source code generated by `scaffold` and compiled/packaged by `build`.
* **Zone 3 (`.candied/games/<TargetName>/`):** Extracted code (`extracted/`), SQLite symbol + FTS5 + asset database (`index.db`), Knowledge Hub docs (`docs/`), extracted assets (`assets/`), live screenshots (`screenshots/`), and semantic control bindings (`controls.json`).

For live execution, **Candied Studio** hosts any game or emulator (`targetPath` + optional `runnerPath`) in two automatic tiers:
* **Tier 1 (`BaseWindow`):** Works **immediately on any game or emulator window** without any plugin (Win32 `PrintWindow`/`BitBlt` screenshots + Win32 Mouse/Keyboard/Gamepad input).
* **Tier 2 (`SensorBridge`):** Upgrades **automatically** when an engine Vision sensor (such as `Candied.VisionSensors.UnityMono`) connects over localhost HTTP, unlocking isolated virtual devices, UI element bounds (`list-ui`), scene graph nodes (`inspect-scene`), and runtime asset inspection (`inspect-runtime-assets`).

## 2. Standard End-to-End Modding Playbook

### Step 1: Audit Target (`inspect`)
Call `inspect(targetPath, runnerPath?)`.
* Inspect `platformId` (e.g., `"unity.mono"` or `"generic.window"`), `architecture`, `runtimeFramework`, `modLoader`, `capabilities`, `modules`, and any returned `platformGuide`.
* Record initial findings or community research via `notes(notes, targetPath)`.

### Step 2: Provision Environment if Needed (`setup`)
If `capabilities` includes `EnvironmentSetup` and `modLoader.isInstalled` is `false` (and the user approved modifying the target copy):
* Call `setup(targetPath)` to install the mod loader and Vision sensor cleanly with `.candied_manifest.json`.
* Use `rollback(targetPath)` whenever the user wants to restore the vanilla directory.

### Step 3: Progressive Code & Asset Discovery (`extract-code`, `query`, `search-code`, `type`)
* Select only the relevant `CoreLogic` / `ModularLogic` module(s) from `inspect` and run `extract-code(moduleName)`. Never extract third-party/framework modules unnecessarily.
* Search symbols with `query(searchTerm, kind?, namespacePrefix?, moduleFilter?)`.
* Search method bodies, string literals, and call sites with `search-code(pattern)`.
* Inspect full or member-filtered class definitions with `type(fullTypeName, signaturesOnly?, memberFilter?)`.
* For visual/data mods, run `index-assets`, `discover-assets`, and `extract-assets` to inspect sprites/textures offline in Zone 3.

### Step 4: Scaffold, Implement & Build (`scaffold`, `build`)
* Call `scaffold(modName, targetPath, includeAssetPipeline?, platformOptions?)` to create `mods/<ModName>/`.
* Implement your mod logic/patches cleanly inside `mods/<ModName>/` (keep custom mod data/presets out of vanilla game save files unless explicitly requested).
* Ensure the game is closed (`game-close`), then run `build(projectFilePath)`.
* If `build` reports missing platform references (for example `CS0012` on `unity.mono`), run the hinted dynamic tool (such as `unity-add-reference(projectFilePath, moduleName, publicize: true)`) and re-run `build`.

### Step 5: Live Visual & Log Verification (`game-launch`, `screenshot`, `send-input`, `trigger-action`, `logs`, `game-close`)
1. Launch directly with `game-launch(targetPath, runnerPath?)`—no pre-registration file is needed.
2. Call `capabilities` and `screenshot` to inspect the live window and confirm the active Vision tier (`BaseWindow` vs `SensorBridge`).
3. Interact using **3-channel `send-input`** (`pointer`, `keyboard`, `gamepad`) or **semantic `trigger-action`** (`get-controls` / `set-controls` / `trigger-action("Confirm")`).
   * In `send-input(channel: "pointer", action: "click", x, y)`, coordinates `(x, y)` are always **top-left pixel coordinates** matching the screenshot PNG.
4. Always call `wait-idle` + `screenshot` after every input to verify real visual changes, and call `logs(minLevel: "Info")` to verify mod initialization and confirm zero runtime exceptions.
5. Finish every live session with `game-close()`.

---

## 3. Operational Guardrails

1. **Test on a copy** whenever possible, and ask before running `setup` or `rollback` on the user's installation.
2. **Never claim a visual outcome without inspecting a follow-up `screenshot`:** HTTP 200 on `send-input` only means the event was dispatched, not that the game reacted.
3. **Persist discovered controls:** When you learn a game's key or controller bindings from code or an options screen, save them with `set-controls` so `controls.json` stays accurate for both AI playbooks and the user's Studio **🎮 Comandi** panel.
4. **Always close before building:** Call `game-close` before `build` to release file locks on deployed mod files.
